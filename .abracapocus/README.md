# SHREDSPACE_1_0

## Purpose

Build ShredSpace 1.0: a performance-responsive dual-voice stereo delay for articulate high-gain lead guitar, as a complete professional C++20 JUCE plugin. Product identity (binding, used consistently in CMake, plugin metadata, and state): project/plugin name ShredSpace, vendor nSpace Systems, version 1.0.0, manufacturer code NSPC, plugin code ShSp, bundle identifier com.nspacesystems.shredspace, LV2 URI urn:nspacesystems:plugin:shredspace. Targets built and verified now: Linux VST3, Linux LV2, Linux Standalone; a windows-msvc CMake preset is generated as configuration only, with the Windows build performed later on Windows tooling per the Aural Maximizer Pro workflow. JUCE is a git submodule at ./JUCE pinned to commit 7c9d3783b127263d72bb65fe0a7e2dc8a02a7ac2 (the revision proven by Aural Maximizer Pro); no task modifies anything under JUCE/. Binding engineering rules restated into every materialized task where applicable: (1) real-time rules - inside processBlock no heap allocation, locks, file IO, profile parsing, string construction, GUI calls, unbounded loops, buffer resizing, FFT allocation, coefficient-object allocation, or destruction of heap-owned objects; all maximum-size buffers allocated in prepareToPlay; juce::ScopedNoDenormals at the top of processBlock. (2) Smoothing by domain - linear SmoothedValue for dB values, Mix, pan, width, signed offsets, normalized controls, cross-feedback, macro/scene/adaptive linear deltas, smoothing dB in dB and converting to linear only afterward via g = 10^(G_dB/20); multiplicative smoothing only for strictly positive values (filter frequency, T60, LFO rate); dedicated transition engines, never ordinary SmoothedValue, for large delay-time changes (Smooth/Bend), routing changes (30 ms wet-path crossfade), profile changes (morph), discrete topology changes, and Hold-loop transitions (30 ms equal-power). Initial smoothing times: gain and Mix 20 ms, filter frequency 50 ms, T60/feedback target 50 ms, width 50 ms, pan 30 ms, normalized expert controls 30 ms. (3) Layering - macros, scenes, and the adaptive engine compute deltas combined into internal effective values (linear: p_eff = clamp(p_base + d_macro + d_scene + d_adaptive, p_min, p_max); dB: same form in dB; octave-scaled: p_eff = clamp(p_base * 2^(d_macro_oct + d_scene_oct + d_adaptive_oct), p_min, p_max)); they never call setValueNotifyingHost on destinations and never rewrite base APVTS values; only explicit profile recall may replace base APVTS values, on the message thread. (4) Cross-thread - profile and adaptive numeric data crosses to the audio thread via two preallocated fixed-size POD buffers with atomic active-index and generation published with release semantics and read with acquire semantics; never std::atomic<std::shared_ptr>; strings and metadata never enter audio-thread snapshots; scalar telemetry via atomics; juce::AbstractFifo only for time-series history where overflow is acceptable. (5) The binding repeat-loop order inside each voice's feedback loop is: fractional delay read, HPF, LPF, Presence Guard, repeat transient softener, mild saturation, restricted diffusion, feedback tap. (6) Feedback is T60-derived, g = 10^(-3*T/T60), always hard-capped at g_final = min(g_requested, 0.985) including during Hold. (7) The performance analyzer runs at a fixed internal 48000 Hz analysis rate behind an anti-alias filter and stateful sample-rate converter regardless of host rate. (8) Delay read positions are always clamped to [8 samples, 8.25 seconds]; maximum delay buffers are 8.25 seconds per channel (about 25.3 MB total at 192 kHz for 2 voices x 2 channels x 32-bit float, which is acceptable). (9) Supported bus layouts are mono-mono, mono-stereo, and stereo-stereo; dry mono input remains center-equivalent in stereo, width is created in the wet path, and unused output channels are initialized deterministically. (10) Testing uses the built-in juce::UnitTest framework with a console runner target executed through CTest; Catch2, GoogleTest, and all other third-party frameworks are forbidden; no new third-party dependency of any kind may be introduced. (11) Because no C++ language adapter exists in the abracapocus registry, every task and phase verification uses explicit cmake configure, cmake --build, and ctest commands appropriate to the touched targets, never the C adapter's default make/cppcheck suggestions. (12) No artist or song names appear in any source file, resource, or profile. Materialized tasks must restate their applicable equations, ranges, defaults, file ownership, forbidden changes, and acceptance criteria directly; no task may say merely 'implement according to the product plan' or receive broad authority over adjacent features.
